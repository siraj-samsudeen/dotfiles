How rama_dw services deploy (gathered by hand during #205, 2026-06-24). The headline: **routine code change → `git push origin main` and the right service auto-deploys.** `deploy.sh` is NOT the routine path.

**Railway — project "Jeyarama-ETL"** (id `a303664d-eb63-4005-adfc-f57447d6ab47`, workspace JeyaRama). Services `gofrugal-extract`, `zakya-extract`, `dbt-runner` are ALL GitHub-connected to `JeyaramaGroup/data-warehouse @ main` and **auto-deploy on push**, gated by per-service **Watch Paths** (`gofrugal_extract/**`, `zakya_extract/**`, `dbt_runner/**`) + a `railway.json` config path. A commit not touching a service's watch path shows `SKIPPED` in its deployment list — **normal, not a failure**. `deploy.sh` per service = one-time provisioning + **secret-variable sync** only (`railway link`, `railway variables --skip-deploys` to push e.g. the MotherDuck token from gitignored `rill/.env`); run it only when secrets change or to (re)provision — push can't inject secrets. **Note:** a watch-path commit touching a service's *vendored* `control_plane/**` redeploys it too — so a control_plane lib change redeploys every migrated extractor (e.g. a zakya lib change also redeploys gofrugal). **4th service: `Postgres`** (id `adc4fb8f-…`, us-west) = the #204 control plane — managed DB, not GitHub-deployed; extractors reach it via `CONTROL_PG_DSN` ref-var (private) or the public proxy `reseau.proxy.rlwy.net:49512` (box/Mac). See [[project_control_plane_204_status]]. **Trigger a one-off cron run:** temp-set the service's cron to a near-future minute via the Railway MCP `update_service` (runs in the *active* deployment — no new deployment row), watch its deploy logs, then restore the schedule.

**Rill — Rill Cloud project `rama-dw`** (org JeyaRama). GitHub-connected; continuous-deploys from `main`'s **`rill/` subpath**. CLI `rill` (authed as siraj@bisquared.com): `rill project status rama-dw`, `rill project refresh rama-dw [--metrics-view <x> | --all]`, `rill project logs`. **GOTCHA:** Rill caches external-MotherDuck-table schemas. After an `ALTER TABLE … RENAME COLUMN` (or any schema change) on a table a metrics view reads, the redeployed view fails with `Binder Error: Referenced column "..." not found` against the *stale* cached schema → fix with `rill project refresh rama-dw --metrics-view <name>`. So when a schema change + Rill yaml change ship together: push → let it deploy → then refresh.

**6th service: `report-server`** (#436, dash.jeyarama.com) — GitHub-connected, Root Dir `/report_server`, but **deploys from the EPIC branch `issue-436-dashboard-serving`, NOT `main`, until the epic merges** (authoritative: `docs/agents/deployment.md`; also wire-report-live Step 8). So a push/merge to `main` touching `report_server/**` does NOT redeploy it — you must land the change on the epic branch (e.g. fast-forward the epic branch to main when it has 0 divergence). This bit me in #514 — see [[project_powerbi_rethink_514]]. The `reports/` folder is a static drop-box (self-contained HTMLs served as-is + auto-listed on the landing page); `out/*.html` are the live daily-rendered dashboards.

**On-prem (NOT GitHub-auto, by design):** only **`sap_bronze`** now runs on the box `rmail@192.168.2.76` (systemd timers; deploy = SSH + update + restart units). See [[reference_sap_bronze_deploy_box]]. (A Railway project named "sap-bronze" also exists under the iab-github workspace — authoritative sap runtime is the box per ADR 0011; treat that Railway project as unverified/possibly-legacy.) **`stylehr_bronze` LEFT the box for Railway** (2026-07-06, #413 / ADR 0045) — now a 5th Railway service `stylehr-bronze` (GitHub-connected, cron `30 4 * * *`, static outbound IPs, region `sfo`); the box timer is retired. SAP stays box-pinned (HANA gateway tunnel, not egress-IP-gated). See [[project_stylehr_railway_413]].
